# 트래픽 스파이크 대비 확장 전략 설계

작성일: 2026-08-10

## 배경

마케팅을 공격적으로 진행할 예정이라 사용자가 한번에 크게 늘어나는 상황을 미리 대비하려 한다. **현재 병목은 없다** — 이 문서는 성능 문제를 고치는 것이 아니라, 아직 오지 않은 스파이크에 대비하는 것이 목적이다.

### 실측한 현재 상태 (2026-08-10)

인프라:

| 항목 | 실측값 |
|---|---|
| 인스턴스 | `i-0bb00c849769dcb7e`, **t2.micro** (1 vCPU / 949MB), ap-northeast-2c |
| 공인 IP | **EIP** `3.34.242.163` (`eipalloc-00be290ccda3d7421`) — stop/start에도 유지 |
| 디스크 | gp3 30GB (62% 사용, 12GB 여유), 3000 IOPS / 125MB/s |
| 로드밸런서 | **없음** (`LoadBalancerNotFound`) |
| TLS | 호스트 nginx + certbot (만료 2026-09-15, 자동갱신 타이머 정상) |
| DNS | Namecheap → EIP A 레코드 직결 |

리소스 사용률 (7일):

| 지표 | 값 | 판단 |
|---|---|---|
| CPU 사용률 | 평균 **0.7%**, 최대 62% | 여유 충분 |
| CPU 크레딧 | **144/144** (최대치), 모드 `standard` | 100% 부하 시 약 2.7시간 뒤 소진 → **10% 하드 스로틀** |
| 메모리 | available **242MB**, **swap 없음** | 초과 시 완충 없이 **OOM Kill** |
| 컨테이너 | frontend 142MB / backend 67MB / postgres 49MB | 프론트 SSR이 최대 소비자 |
| DB 크기 | **7.4MB**, 커넥션 10/100 | 튜닝 불필요 |

운영 안전망:

- CloudWatch 알람 **0개**
- EBS 스냅샷 **0개**, DLM 정책 **0개**
- DB 백업 **없음**
- nginx 설정이 서버의 `/etc/nginx/nginx.conf` 한 파일에만 존재, **버전 관리 안 됨**

### 실제 트래픽 경로

```
dngg.one ──DNS(Namecheap)──→ EIP 3.34.242.163 ──→ EC2 t2.micro
                                                    └─ nginx (호스트, 80/443, certbot)
                                                         ├─ /      → :3000 frontend (docker)
                                                         └─ /api/  → :3010 backend  (docker)
                                                                       └─ postgres (docker, ./pg-data)
```

`start-dngg.sh`에는 ALB DNS(`dngg-1671377533.ap-northeast-2.elb.amazonaws.com`)가 적혀 있으나 **해당 로드밸런서는 존재하지 않는다.** 과거 `full-stop-dngg.sh`(로드밸런서 삭제 포함)가 실행된 뒤 재생성되지 않은 것으로 보인다. 이 스크립트들의 안내 문구는 실제와 다르므로 갱신 대상이다.

## 목표

1. 예고 없는 트래픽 급증에 서비스가 **통째로 내려가지 않는다.**
2. 용량이 필요해지는 순간을 **놓치지 않고 감지**하고, 그때 몇 분 안에 늘릴 수 있다.
3. 최악의 경우에도 **데이터를 잃지 않는다.**

## 제약

- **실제 트래픽이 증가하기 전까지는 비용이 늘지 않아야 한다.** 이 제약이 설계를 사실상 결정했다.
- 트래픽이 실제로 왔을 때 감당 가능한 상한은 월 $30~50.
- 목표 규모는 **수백 그룹 / 동시 수십 명**. (현재 운영 계정 10여 개)

## 비목표

- 앱 인스턴스 다중화(스케일 아웃) — 목표 규모에서 불필요하다. L3 항목으로 문서화만 한다.
- 관리형 DB(RDS) 이전 — 지금부터 월 $15~25가 발생해 제약과 충돌한다. L2 항목으로 문서화만 한다.
- 서버리스 재플랫폼(Vercel + Neon 등) — 제약에는 잘 맞으나 CI/CD·compose·배포 파이프라인을 전부 다시 짜야 해서 마케팅 직전에 할 일이 아니다.
- **Postgres 튜닝** — DB가 7.4MB이고 커넥션이 10/100이라 튜닝할 것이 없다. 이득 없이 리스크만 생기므로 **의도적으로 제외**한다.
- **컨테이너 `mem_limit`** — 949MB 환경에서 상한을 잘못 잡으면 swap이 있어도 컨테이너 단위 OOM이라는 새 실패 모드를 만든다. 부하 테스트에서 특정 컨테이너의 비정상 증가가 관측되면 그때 재검토한다.

## 핵심 판단

**지금 리스크의 정체는 용량 부족이 아니라 완충장치 부재다.** CPU를 0.7%밖에 안 쓰는데도 서비스를 잃을 수 있는 이유는 셋이고, 셋 다 돈이 아니라 설정으로 해결된다:

1. swap이 없어 메모리 초과가 곧 프로세스 사망
2. `standard` 크레딧 모드라 크레딧 소진이 곧 하드 스로틀
3. 백업이 없어 인스턴스 유실이 곧 데이터 유실

세 실패 모두 **서서히 나빠지지 않고 절벽처럼 떨어진다.** 스파이크 대비 관점에서 가장 나쁜 형태다. 용량 자체는 인스턴스 타입 전환 한 번으로 살 수 있고, 그건 실제로 트래픽이 왔을 때 하면 된다.

## 설계

### 1. 확장 레버와 트리거

구조는 바꾸지 않는다. 대신 확장을 단계별 레버로 정의하고 **언제 당길지**를 지표로 못 박는다.

```
[L0] 현재 + 완충장치       t2.micro 1대, nginx, 컨테이너 3개    $0 추가       ← 지금 적용
      ↓ 크레딧 잔량 < 50 OR available 메모리 < 150MB OR p95 > 1s
[L1] 수직 확장             t3.small (2 vCPU / 2GB)             +$9/월       ← 리허설까지
      ↓ t3.small에서 CPU 평균 > 40% OR DB 커넥션 포화
[L2] DB 분리               RDS db.t4g.micro 또는 별도 EC2       +$15~25/월   ← 문서만
      ↓ 수직 확장으로 감당 불가 (목표 규모에선 사실상 도달 안 함)
[L3] 앱 다중화             ASG + 코드 제약 3종 해결             +$20~/월     ← 문서만
```

레버별 준비 수준을 의도적으로 다르게 둔다. L1은 실제로 리허설해 다운타임과 절차를 확보하고, L2·L3은 선행 조건만 문서로 남긴다.

**L3의 선행 조건 (지금 고치지 않는다)** — 백엔드를 2대 이상으로 늘리면 다음이 깨진다:

- `LoginThrottlerGuard` — `@nestjs/throttler` 6.5.0 기본 스토리지가 프로세스 메모리 `Map`이라 인스턴스마다 카운터가 따로 돈다. 유효 한도가 N배로 느슨해지는데 **코드상 아무 감지 신호가 없다.** 공유 스토리지(Redis 등)로 옮겨야 한다.
- `subscription-renewal.cron.ts`의 `@Cron(EVERY_DAY_AT_4AM)` — 인스턴스 수만큼 중복 발화한다.
- `synchronize: true` — 여러 인스턴스가 동시 부팅하며 스키마를 고치려 든다.

**L1 실행 시 선행 조건** — 인스턴스 타입 변경은 stop/start이고, 그건 백엔드 재시작이며, `synchronize: true`는 재시작마다 스키마를 실제 DB에 맞춘다. 즉 **확장 작업 자체가 스키마 변경 트리거다.** 평소엔 no-op이지만 배포 스큐 상태에서 확장하면 사고가 된다. 런북에 "확장 전 프론트·백엔드 배포 상태 확인"을 선행 조건으로 넣는다.

### 2. 완충장치 (지금 적용, 추가 비용 $0)

**2.1 swap 2GB**

`/swapfile` 2GB 생성, `vm.swappiness=10`, `/etc/fstab` 등록. 디스크 여유 12GB 중 2GB를 쓴다.

메모리 부족의 결과를 "프로세스 사망"에서 "느려짐"으로 바꾼다. swappiness를 낮게 두어 평소에는 쓰지 않고 정말 급할 때만 쓰게 한다. gp3 3000 IOPS라 스왑 성능도 나쁘지 않다.

**2.2 CPU 크레딧 `standard` → `unlimited`**

`aws ec2 modify-instance-credit-specification`. 재부팅 불필요, 즉시 적용.

제약("트래픽 전엔 비용 증가 없음")에 가장 정확히 맞는 조치다. 평소 사용률이 0.7%이므로 **$0**이고, baseline(10%)을 초과해 실제로 쓴 만큼만 vCPU-시간당 $0.05가 붙는다.

이론적 최대 비용: 1 vCPU를 한 달 내내 100%로 태워도 `720h × 0.9 × $0.05 ≈ **$32/월**`이 상한이다. 예산 안에 들어오므로 폭주 리스크는 없다. 그래도 AWS Budgets 알람(무료)으로 감시한다.

**2.3 죽은 `postgresql.conf` 마운트 제거**

compose가 `./postgresql.conf:/etc/postgresql.conf`를 마운트하는데, 서버에 해당 파일이 없어 **Docker가 빈 디렉토리를 만들어 놓았다**:

```
drwxr-xr-x. 2 root root 6 May 13 2025 postgresql.conf   ← 파일이 아니라 디렉토리
```

게다가 postgres:15는 `/etc/postgresql.conf`를 읽지 않는다 (실효 `config_file`은 `/var/lib/postgresql/data/postgresql.conf`). 이 마운트는 아무 일도 하지 않으면서 **튜닝이 적용되고 있다는 착각만 만든다.** compose에서 제거한다.

**2.4 TypeORM 커넥션 풀 명시**

현재 `app.module.ts`에 풀 설정이 없어 node-postgres 기본값 10이 우연히 적용되고 있다. `extra: { max: 10, connectionTimeoutMillis: 5000 }`로 명시해, 스파이크 때 커넥션 획득 대기가 무한정 쌓이지 않고 빠르게 실패하게 한다. L1 확장 시 20으로 올리는 것을 런북에 포함한다.

### 3. 방어 (지금 적용, 비용 $0)

**3.1 보안 그룹 축소**

현재 `sg-035e49b91ab5412e2`의 인그레스:

| 포트 | 소스 | 조치 |
|---|---|---|
| 80, 443 | 0.0.0.0/0 | 유지 |
| **3010** | **0.0.0.0/0** | **제거** |
| **22** | **0.0.0.0/0** | **본인 IP로 축소** |
| all (-1) | 본인 IP 4개 | 유지 |

`NEXT_PUBLIC_API_URL=https://dngg.one/api`이므로 프론트는 nginx만 경유한다. **3010 직접 노출은 불필요하며**, 열려 있는 동안은 nginx의 rate limit이 `http://3.34.242.163:3010`으로 통째로 우회된다. (`PROJECT_CONTEXT.md`가 언급한 mixed-content 차단은 브라우저에만 적용되고 스크립트·봇에는 적용되지 않는다.)

22는 이미 본인 IP 4개가 전체 허용(-1)으로 등록돼 있어 축소해도 접속에 지장이 없다.

**3.2 nginx 강화**

- `limit_req` 도입 — IP당 요청 제한. 백엔드에 닿기 전에 걸러낸다.
- `gzip` 활성화 — 현재 꺼져 있다. 대역폭과 체감 속도에 직접 효과.
- access log 포맷에 `$request_time` 추가 — 4절 관측의 입력이 된다.
- 현재 `worker_connections 1024`, `worker_processes auto`(1 vCPU → 1). 목표 규모에는 충분하므로 유지한다.

**3.3 전역 로그인 rate limit을 환경변수로**

`SITEWIDE_LOGIN_THROTTLE_LIMIT = 300` / TTL 5분이 **코드 상수**다. 이건 IP별이 아니라 **전역 단일 버킷**이라, 누가 채우든 그 5분 동안 모든 사용자가 429를 받는다. 스프레이 공격 방어로는 옳은 설계지만 **마케팅 스파이크 자체가 이 한도를 칠 수 있다** — 초당 1회꼴이다.

지금 구조에서는 한도를 올리려면 재빌드·재배포가 필요하다. 이를 환경변수로 빼서 `.env` 수정 + 컨테이너 재시작만으로 조정 가능하게 한다. 기본값은 300을 유지한다. 429 발생률 알람을 함께 건다.

### 4. 관측 (지금 적용, 비용 $0)

현재 알람이 0개다. 무슨 일이 나도 사용자가 알려주기 전에는 알 수 없다.

**4.1 헬스체크 엔드포인트**

- `GET /health` — liveness. 앱 프로세스 생존만 확인.
- `GET /health/ready` — readiness. **DB 연결까지 확인**한다.

현재 CI 헬스체크는 `/group/all`을 쓰는데, 이는 인증 없는 데이터 엔드포인트라 헬스체크용으로 부적절하다. `.github/workflows/deploy.yml`도 `/health/ready`로 교체한다.

`@nestjs/terminus`는 이 용도에 과하므로 직접 구현한다.

**4.2 CloudWatch 알람** (무료 티어 10개 내)

| 알람 | 임계치 | 용도 |
|---|---|---|
| `CPUCreditBalance` | < 50 | **L1 트리거** |
| `StatusCheckFailed` | >= 1 | 인스턴스 자체 장애 |
| AWS Budgets | 예산 초과 | `unlimited` 전환 후 과금 감시 |

SNS 이메일 구독으로 알림을 받는다.

**4.3 메모리·디스크·5xx·응답시간은 자체 스크립트로**

CloudWatch 에이전트의 커스텀 메트릭은 개당 월 $0.30라 제약에 걸린다. 대신 서버 cron + SNS publish(이메일 월 1000건 무료)로 5분마다 확인한다:

- available 메모리 < 150MB → **L1 트리거**
- 디스크 사용률 > 80%
- nginx access log 기준 5xx 비율, p95 응답시간(`$request_time`)
- 로그인 429 발생률

### 5. 백업 (지금 적용, 월 $1~2)

현재 스냅샷도 DLM도 없다. 인스턴스가 유실되면 **DB도 nginx 설정도 복구할 수 없다.**

**5.1 nightly `pg_dump` → S3** (월 $0.01 미만)

DB가 7.4MB라 gzip하면 1MB 미만이다. 가장 싸고 복구가 빠른 보호막이다. 30일 보관.

**5.2 설정 파일 백업**

`nginx.conf`, 루트 `.env`, `docker-compose.yaml`을 함께 백업한다. nginx 설정이 서버 한 곳에만 있고 버전 관리가 안 돼, 인스턴스 유실 시 TLS·프록시 설정을 처음부터 다시 짜야 한다. `.env`는 시크릿이므로 저장소가 아니라 **S3 암호화 버킷**에 둔다.

**5.3 주 1회 EBS 스냅샷 (DLM), 4주 보관** (월 $1~2)

전체 시스템 복구용. 이 설계에서 **유일하게 지금 비용이 발생하는 항목**이다. 데이터 보호는 트래픽과 무관하게 필요하다고 판단해 포함했다. 제외하더라도 5.1로 데이터 자체는 지켜진다.

**5.4 복구 리허설 1회**

덤프에서 실제로 복원되는지 확인한다. 복구해본 적 없는 백업은 백업이 아니다.

## 실행 순서

되돌릴 수 있는 변경이라도 순서가 틀리면 안전망 없이 서버를 만지는 셈이 된다.

```
1) 백업 구축·검증  →  2) 완충장치(swap·크레딧·마운트·풀)  →  3) 방어(SG·nginx·429 env화)
   →  4) 관측(/health·알람)  →  5) 부하 테스트  →  6) L1 리허설
```

5·6이 유일하게 서비스에 영향을 줄 수 있는 작업이라 맨 뒤에 둔다.

## 검증

### 부하 테스트

1절의 트리거 임계치(크레딧 50, 메모리 150MB, p95 1초)는 아직 추정치다. 실측으로 검증한다.

- **도구**: k6, 로컬에서 `https://dngg.one` 대상
- **대상**: 읽기 경로 위주 (경기 요약, 랭킹, `/group/all`)
- **로그인 경로 제외** — 3.3의 전역 429 버킷을 테스트가 스스로 소진시켜 실제 사용자를 잠근다. 로그인 한계는 별도로 소량만 확인한다.
- **램프업**: 동시 10 → 25 → 50 → 100, 각 3분
- **동시 측정**: p50/p95/p99, 에러율, available 메모리, swap 사용량, `CPUCreditBalance` 소모 속도
- **중단 조건**: 에러율 5% 초과 시 즉시 중지
- **시점**: 사용자가 적은 새벽. 현재 실사용 계정이 10여 개라 영향이 작다.
- **산출물**: "동시 N명에서 p95가 1초를 넘고, 크레딧이 시간당 X씩 준다" — L1 트리거의 근거이자 마케팅 규모 상한선

**알려진 한계**: 로컬에서 쏘면 집 네트워크가 먼저 병목일 수 있어, 측정된 한계가 서버가 아니라 회선의 한계일 가능성이 있다. 응답이 작은 JSON이라 대체로 괜찮지만, 결과가 이상하면 같은 리전에 임시 인스턴스를 띄워 재측정한다.

### L1 리허설

t2.micro → t3.small → t2.micro 왕복을 실제로 수행한다. 목적은 용량 확보가 아니라 **절차 검증**이므로 끝나면 되돌린다.

확인할 것:

- 실제 다운타임 (런북에 기록)
- **EIP 유지 여부** — 붙어 있으니 유지되어야 하지만, 틀리면 DNS 갱신까지 사이트가 죽는다. 반드시 검증.
- **`synchronize: true`가 재기동 때 스키마를 건드리지 않는지** — 백엔드 로그로 확인
- `restart: always`로 컨테이너 3개 자동 기동, nginx·certbot 정상 여부
- t3 계열은 기본이 `unlimited` 모드이고 Nitro 기반이라 부팅 실패 여부를 확인

### 수용 조건

- swap 활성 + `swappiness=10` 확인
- 크레딧 모드 `unlimited` 확인
- **`/health/ready`가 DB를 끊었을 때 실제로 실패하는지** — 무조건 200을 뱉는 헬스체크는 없느니만 못하다
- **알람이 실제로 메일을 보내는지** — 임계치를 임시로 낮춰 발화 확인
- 3010 차단 후에도 사이트 정상 동작
- **pg_dump가 S3에 올라가고, 그 덤프에서 로컬 복원이 성공하는지** — 행 수 대조까지

### 롤백

모든 변경은 독립적으로 되돌릴 수 있어야 한다.

| 변경 | 롤백 |
|---|---|
| SG 축소 | 규칙 재추가 (즉시) |
| nginx | 변경 전 conf 백업 → `nginx -t` 통과 후 `reload`(restart 아님) |
| swap | `swapoff -a` + fstab 항목 제거 |
| 크레딧 모드 | `standard`로 복귀 |
| 인스턴스 타입 | stop → 타입 되돌리기 → start |

## 부수 정리

- `start-dngg.sh` / `stop-dngg.sh` / `full-stop-dngg.sh` / `optimize-lb.sh`가 존재하지 않는 로드밸런서를 참조한다. `full-stop-dngg.sh`는 이미 삭제된 LB를 다시 지우려 하고, `optimize-lb.sh`는 실행하면 실패한다. 안내 문구를 실제 구조(EIP 직결)에 맞게 갱신하거나 제거한다.
- `CLAUDE.md`·`PROJECT_CONTEXT.md`의 배포 구조 설명에 nginx 리버스 프록시 계층이 빠져 있다. 보강한다.

## 미해결 / 후속

- L2(DB 분리) 실행 시 `pg-data` 바인드 마운트에서 관리형 DB로 옮기는 절차는 별도 설계가 필요하다.
- 백엔드 컨테이너 Dockerfile이 아직 `node:20`이고 CI는 Node 22다 (`CLAUDE.md` 참고). 이번 범위는 아니지만 L1/L3 전환 시 함께 정리하는 편이 좋다.
