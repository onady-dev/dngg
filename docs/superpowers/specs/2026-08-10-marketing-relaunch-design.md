# 마케팅 재개 — 설계 (제로 예산)

- 작성일: 2026-08-10
- 대상: dn.gg — 아마추어 농구 경기 기록·랭킹 앱
- 상태: 설계 승인됨
- 선행 문서: `docs/superpowers/specs/2026-07-19-marketing-gtm-design.md` (GTM 전략),
  `docs/superpowers/plans/2026-07-19-marketing-phase0.md` (Phase 0 체크리스트)
- 제약: 예산 0원, 대표 가용 시간 주 2~4시간(개발 제외)

## 0. 왜 이 문서가 기존 GTM 문서를 대체하는가

2026-07-19 GTM 문서는 "이탈 = 제품핏/온보딩 문제"를 암묵적 전제로 깔고 90일 내 활성 그룹
50개를 목표로 잡았다. **그 전제가 틀렸다.** 이탈의 실제 원인은 버그였고, 이미 수정·배포됐다.
목표 숫자도 실적(18개월간 외부 팀 4팀)과 어긋나 그대로 쓸 수 없다.

이 문서는 정정된 진단 위에서 순서와 목표를 다시 잡는다. GTM 문서의 포지셔닝·메시지·채널
우선순위(1~4절)는 유효하므로 계속 참조한다.

## 1. 진단 — 확정된 사실

운영 DB(2026-08-10 실측)와 코드로 확인한 것만 적는다.

### 1.1 이탈은 마케팅 문제가 아니라 버그였다

가입으로 그룹이 생성될 때 `logitem`(득점·리바운드 등 기록 항목)이 시드되지 않았다.
기록 화면은 항목을 버튼으로 그리므로, 항목이 0이면 **누를 것이 아무것도 없다.**
안내도 에러도 없는 조용한 막다른 길이다.

| 그룹 | 가입일 | 경기 | **기록된 로그** | 소유자 | 연락 |
|---|---|---|---|---|---|
| 스내치 (1) | 2025-07-15 | 72 | 6,289 | 본인 팀 | — |
| 농우회 (10) | 2026-06-23 | 12 | **1,338** | anst23 | 대표 직접 |
| Breakers (14) | 2026-08-01 | 2 | **0** | junwonjang7@naver.com | ✉️ 메일 가능 |
| 해롱해롱팀 (11) | 2026-07-01 | 3 | **0** | harryk1m | ❌ 이메일 아님 |
| Tachy (7) | 2026-01-28 | 1 | **0** | lenny5953 | ❌ 이메일 아님 |
| 86ers (8) | 2026-02-04 | 0 | 0 | 86ers | ❌ 이메일 아님 |

(테스트/본인 계정: 테스트(9), sweep(13), NE(12), HP(15) — 분석에서 제외)

경기를 만든 이탈 팀(Breakers·해롱해롱팀·Tachy) **전원이** 로그를 한 줄도 남기지 못했다.
86ers는 경기 생성 전에 이탈했다. 제품을 안 좋아해서 떠난 게 아니라 **쓸 수가 없었다.**

### 1.2 수정은 이미 배포되어 있다

- 수정 커밋 `002248e` (2026-08-06) — `seedLogitemsForGroup`을 그룹 생성 경로 두 곳
  (`POST /user` 가입, `POST /group`) 모두에서 호출.
- 운영 백엔드 `sha-5076c709`에 포함됨을 확인(`git merge-base --is-ancestor` 통과).
- 배포본 이후 main에 대기 중인 백엔드 변경 없음.
- 코드는 견고한 편이다: 가입은 트랜잭션 안에서 그룹 생성과 원자적으로 묶이고, 템플릿
  그룹(`TEMPLATE_GROUP_ID = 0`)이 비어 있어도 `DEFAULT_LOGITEMS`로 폴백한다.

**회귀 검증 완료(2026-08-10).** 로컬 전체 스택에서 신규 가입 → 선수 추가 → 경기 생성 →
로그 기록 6건 → 랭킹·능력치 반영까지 실행으로 확인했다. 신규 그룹에 logitem 10개가
시드되고 기록 화면에 항목 버튼이 정상 렌더된다. 유입 개시 게이트를 통과했다.

### 1.3 인프라 선행조건은 해소됐다

- **SES 프로덕션 승인 완료** (`ProductionAccessEnabled: true`, 5만통/일, 14통/초).
  Phase 0의 최대 블로커였고, 기존 메모리에 "샌드박스"로 남아 있던 정보는 낡은 것이다.
- GA4 라이브 (`G-VVC37NHFYB`), 랜딩 히어로·온보딩 체크리스트 배포됨.
- 선수 능력치 OG 카드(`/player/[id]/opengraph-image.tsx`) 동작 중.

### 1.4 남은 제품 구멍

- **`dngg.one` 루트에 openGraph 메타가 없다.** 카톡·밴드에 도메인 링크를 붙이면 미리보기
  카드가 비어 나간다. 이번 계획의 채널 3종이 전부 "링크 뿌리기"라 직접적인 손실이다.
- 신규 그룹이 기록 불가 상태가 되어도 **감지할 장치가 없다.** 이번 사고가 6개월 넘게
  방치된 이유가 이것이다.

## 2. 순서와 게이트

```
C. 회귀 검증  ──(게이트)──→  D. 루트 OG  ──→  유입 개시(플레이북)
                                  │
                              E. 활성화 감지 ──→ F. 주간 리포트 자동화 (상시)
```

E가 감지할 사실을 만들고, F가 그것을 매주 손에 쥐어준다. 둘은 한 묶음이다 — E만 있고 F가
없으면 쿼리는 존재하되 아무도 안 돌린다.

**회귀 검증 통과가 유입 개시의 게이트다.** 깔때기가 막혀 있는지 모르는 채로 유입을 부으면
이번 사고가 그대로 재현되고, 제로 예산에서 소모성 자산인 커뮤니티 채널만 태운다.

### 범위에서 뺀 것 (판단 근거 포함)

- **자가 복구 UI**(기록 화면 logitem 0일 때 복구 버튼) — 사용자 판단으로 제외. 수정이
  배포됐으므로 E(감지)가 안전망 역할을 대신한다. → **E의 주간 확인 쿼리는 생략 불가 항목이 된다.**
- **NE(그룹 12) 데이터 수선** — 사용자 판단으로 제외. 본인 소유 계정이라 실사용 영향 없음.
- 경기결과·데일리 공유 카드 — 활성 팀 2팀으로는 어느 카드가 먹히는지 측정이 불가능하다.
  팀이 늘어난 뒤에 만들어야 판단 근거가 생긴다.
- 그룹 초대 링크 — 현재 병목은 팀 내 정착이 아니라 팀 획득이다. 또한 `Player`와 `User`가
  별개 엔티티라 초대 링크가 줄여주는 노동이 무엇인지 불분명하다.
- SEO 정적 렌더 — `/`가 `!mounted → null` 클라이언트 렌더라 네이버 크롤러 기준 자산이
  사실상 0이지만, 이번 6주의 채널 3종은 검색 유입이 아니다. 별도 과제.
- 인스타그램 계정 — 활성 팀 2팀이면 콘텐츠 원료가 없다.
- 유료 광고 — 예산 0 전제.

## 3. 제품 작업 (개발)

### C. 회귀 검증 — 유입 개시의 게이트

가입 → 선수 추가 → 경기 생성 → **로그 기록 성공**까지 실제로 통과하는지 확인한다.
코드 판독이 아니라 실행으로 확인해야 한다. 로컬 전체 스택에서 신규 계정으로 수행하며,
운영 DB에 테스트 그룹을 만들지 않는다.

확인 항목:
- 신규 가입 그룹에 logitem 10개가 시드되는가
- 기록 화면에 항목 버튼이 그려지는가
- 로그가 저장되고 집계(랭킹·능력치)에 반영되는가

**통과 실패 시 이 문서의 나머지는 전부 보류한다.**

### D. 루트 OG 카드

- `frontend/src/app/layout.tsx`의 `metadata`에 `openGraph` 블록 추가.
  `metadataBase`는 이미 설정되어 있다(`NEXT_PUBLIC_API_URL` origin 기준).
- `frontend/src/app/opengraph-image.tsx` 신규 — `next/og`로 1200×630 PNG.
- 기존 검증된 패턴을 그대로 따른다(`/player/[id]/opengraph-image.tsx`):
  Pretendard 폰트를 `frontend/public/fonts`에서 `fs.readFile`로 로드(한글 렌더 필수),
  다중 자식 `div`에 `display:flex` 명시(Satori 요구사항).
- 카드 내용: 서비스명 + 한 줄 가치 메시지 + 대표 시각 요소. 팀별 동적 데이터는 넣지 않는다
  (루트 URL은 특정 팀에 속하지 않는다).
- 검증: 배포 후 카카오톡·밴드에 `https://dngg.one` 붙여넣어 카드 렌더 확인.

### E. 활성화 감지

- GA 이벤트 `first_log_recorded` 추가 — 그룹이 **처음으로 로그를 남긴 순간**. 가입이 아니라
  이 이벤트가 진짜 활성화 지표다. 기존 `track()` 추상화(`frontend/src/lib/analytics.ts`)를 쓴다.
- 감지 쿼리 1개 — "최근 **14일** 내 생성된 그룹 중 경기는 만들었는데 로그가 0인 그룹".
  기간이 7일이 아닌 이유: 동호회 경기 주기가 주 1회 수준이라 7일 창은 "아직 안 모인 팀"과
  "막힌 팀"을 구분하지 못한다. 런북에 복붙 가능한 형태로 기록한다.
- **이 절은 감지할 사실을 정의할 뿐, 발송은 F-1이 맡는다.** 쿼리만 만들고 자동 발송을 붙이지
  않으면 아무도 안 돌린다.
- 이 쿼리가 걸리면 해당 총무에게 즉시 연락한다. 이번 사고를 하루 만에 잡았을 유일한 장치다.

### F. 주간 리포트 자동화 (알림)

주간 루틴이 두 성격으로 갈린다. 지표 확인은 **알림이 아니라 결과 자체**를 받을 수 있고,
사람 활동(카페 상주·1:1 접촉)은 순수 리마인더가 필요하다. 둘을 다른 장치로 처리한다.

**F-1. systemd 타이머 + SNS 메일 — 지표 리포트 (안전망)**

서버에 이미 같은 패턴이 셋 돌고 있으므로 새 메커니즘을 만들지 않고 그대로 따른다:
`dngg-monitor.timer`(5분) / `dngg-backup-db.timer`(일간) / `dngg-backup-config.timer`(주간).
스크립트는 `/usr/local/project/dngg/scripts/`에 두고, 알림은 기존 SNS publish 경로를 쓴다.

- 신규 유닛: `dngg-weekly-report.timer` + `.service` + 스크립트. 월요일 아침 발화.
- 리포트에 담을 것: 신규 그룹 수, **경기는 있는데 로그 0인 그룹**(E의 감지 쿼리),
  그룹별 주간 로그 증분, 그룹 14(Breakers) 로그 수 변화(4.4 복구 결과 추적).
- 비용 0(SNS 월 1,000건 무료), Claude·PC 없이 영구 동작. 이것이 안전망이다.
- 나머지 인프라와 마찬가지로 유닛 파일·스크립트는 저장소에서 버전 관리한다.

**F-2. Claude 주간 스케줄 — 해석 + 사람 활동 리마인더**

`/schedule` 스킬로 주간 cron 클라우드 에이전트를 등록한다. 숫자를 5절의 판단 기준과 대조해
"지금 무엇을 해야 하는지"까지 낸다. 예: "그룹 14 로그 여전히 0 → 복구 메일 무반응, 2주
경과로 실패 처리", "신규 그룹 3팀 중 2팀 로그 0 → 회귀 의심".

**캘린더를 쓰지 않기로 했으므로 4.5의 사람 활동 리마인더도 이쪽이 겸한다.** 주간 알림에
이번 주 해야 할 활동(카페 상주 2회·결과 카드 공유·격주 1:1 접촉)을 함께 싣는다. 이 역할을
빼면 사람 활동은 알림 없이 방치된다.

F-1과 병행한다 — F-1이 Claude와 무관하게 도는 안전망, F-2가 해석 레이어다.

## 4. 실행 플레이북 (주 2~4시간)

### 4.1 채널 1 — 농우회 레퍼럴 (최우선)

시간당 효율이 가장 높다. 신뢰 기반이라 전환율이 다른 채널과 자릿수가 다르다.

**30분 인터뷰 1회**로 두 가지를 동시에 얻는다:
1. 메시지 카피의 원료 — 왜 계속 쓰는지(본인 언어로), 버그 시기에 어떻게 항목이 있었는지,
   불편한 점. 특히 **버그가 살아 있던 6/23에 가입하고도 혼자만 1,338개를 기록한 이유**는
   반드시 확인한다. 대표가 직접 셋업을 도왔다면 "사람이 붙으면 남는다"의 증거이고,
   아웃리치에 시간을 쓰는 근거가 된다.
2. 소개 요청.

**소개 요청은 구체적으로 한다.** "아는 팀 소개해주세요"는 전환이 0에 수렴한다. 상대가
머릿속에서 이름을 떠올릴 수 있는 형태로 묻는다: "같은 체육관 쓰는 팀", "정기전 상대팀",
"리그 같은 조 팀". 목표 3~5팀.

### 4.2 채널 2 — 네이버 카페·밴드 시딩

물량은 가장 크지만 **커뮤니티는 제로 예산에서 소모성 자산이다.** 스팸으로 한 번 찍히면
그 카페는 다시 못 쓴다.

- 가입 직후 홍보 글은 밴 직행. **2주간 눈팅·댓글로 활동 이력을 쌓은 뒤** 본 게시물.
- 형식은 홍보가 아니라 콘텐츠: "우리 팀 8월 랭킹" + 능력치 카드 이미지를 올리고 도구는 각주로.
- 카페 2~3곳, 주 1회. 매번 카페 규칙 확인.

### 4.3 채널 3 — 카카오 오픈채팅

그룹 생성 전환은 낮지만 **총무가 누군지 알아내는** 채널이다.

- "농구" + 지역으로 방 3~5개 상주.
- 홍보 금지방이 대부분이라 상주하며 질문에 답하는 형태로만 노출한다.

### 4.4 복구 메일 — Breakers (발송 완료)

`junwonjang7@naver.com`. 8/1 가입, 선수 34명을 직접 등록하고 경기 2개를 만들었으나 로그 0.
**수정 5일 전에 겪었다.** 진지하게 셋업했던 팀이고, 유일하게 연락 가능한 피해 팀이다.

**2026-08-10 대표가 직접 복구 메일 발송 완료.** 남은 것은 결과 확인이다:
- 회신이 오면 → 1:1 셋업 지원을 제안한다(농우회 사례상 사람이 붙은 팀이 남는다).
- 회신이 없어도 **재방문·기록 재개 여부는 DB로 확인된다** — 그룹 14의 로그 수가 0에서
  움직이는지 4.5 주간 지표 확인에 포함한다. 2주 내 무반응이면 복구 실패로 처리한다.

| 월 | F-1 리포트 메일 읽기 (직접 쿼리 불필요) | 2분 | F-1 자동 발송 |
| 주중 2회 | 카페·밴드·오픈채팅 상주 | 30분 ×2 | F-2 |
| 주말 경기 후 | 자기 팀 결과 카드 공유 | 30분 | F-2 |
| 격주 | 총무 1:1 접촉 3건 | 30분 | F-2 |

주당 합계 약 1시간 40분으로, 예산(2~4시간) 안에 여유를 남긴다. 남는 시간은 인입된 총무
응대에 쓴다 — 문의 응대는 예측이 안 되므로 루틴에 고정하지 않는다.

### 4.6 함께 만들 자료

- 총무 1:1 메시지 템플릿 (레퍼럴 소개받은 팀용 / 오픈채팅에서 발견한 총무용)
- 카페 게시물 초안 (홍보가 아닌 콘텐츠 형식)
- 농우회 인터뷰 질문지 (4.1의 두 목적을 30분 안에)

(Breakers 복구 메일 문안은 발송 완료로 불필요 — 4.4 참조)

## 5. 6주 후 판단 기준

기준을 미리 못 박지 않으면 6주 뒤에 "느낌상 별로였다"로 끝난다.

판정은 위에서부터 순서대로 적용하고, 먼저 걸리는 것을 택한다.

| # | 결과 | 정의 | 다음 행동 |
|---|---|---|---|
| 1 | **유입 O / 활성화 X** | 신규 외부 그룹 3팀+ 인데 **로그 100개+ 도달이 1팀 이하** | 마케팅 중단. 온보딩·제품으로 회귀 — 유입이 아니라 제품이 문제다 |
| 2 | **성공** | 신규 외부 그룹 5팀+ , 그중 3팀+ 가 로그 100개+ | 채널 유지, 물량 확대. 공유 카드 확장 착수 |
| 3 | **부분 성공** | 신규 외부 그룹 3~4팀, 활성 전환은 정상 | 채널 유지. 물량만 늘려 6주 더 |
| 4 | **유입 X** | 신규 외부 그룹 2팀 이하 | 채널 또는 메시지 재선택 |

"로그 100개+"를 활성 기준으로 삼는 근거: 농우회는 12경기에 1,338개(경기당 약 110개)를
기록했다. 즉 **로그 100개 ≈ 실제 경기 한 판을 끝까지 기록했다**는 뜻이고, 이것이 제품이
의도대로 동작한 최소 증거다.

기준선(2026-08-10): 외부 활성 그룹 1팀(농우회), 누적 외부 그룹 4팀.

## 6. 리스크

- **회귀 검증을 건너뛰고 유입을 시작하는 것** — 이번 사고의 완전한 재현. 게이트로 막는다.
- **자가 복구 UI를 넣지 않기로 했으므로 감지가 유일한 안전망이다.** F-1(서버 타이머)이
  Claude와 무관하게 돌아 이 위험을 덮는다. F-1 없이 F-2에만 의존하면 안전망이 Claude
  가용성에 묶인다.
- **커뮤니티 밴** — 채널이 영구 소실된다. 2주 활동 이력 + 콘텐츠 형식으로 완화한다.
- **대표 시간이 병목** — 주 2~4시간을 넘기는 계획은 실행되지 않는다. 루틴을 이 예산 안에 가둔다.
- **연락 불가 이탈 팀 3곳**(해롱해롱팀·Tachy·86ers) — 레거시 아이디라 이메일이 없다.
  복구 불가로 처리한다. 향후 가입은 이메일 인증을 거치므로 같은 상황은 재발하지 않는다.
