# 경기 시즌 배정 설계

작성일: 2026-08-18

## 배경

시즌제 1단계(`2026-08-14-season-design.md`)는 **경기의 시즌 귀속을 생성 시점 스냅샷으로만**
결정했다. `Game.seasonId`는 경기를 만들 때 `Group.currentSeasonId`를 복사해 채우고, 그 이후로는
바뀌지 않는다. 시즌 도입 이전 경기는 전부 `seasonId = null`로 남기고 소급 이관은 하지 않기로
했다.

그 결과 실제로 두 가지 문제가 드러났다.

**1. 시즌을 만들어도 과거 기록이 들어가지 않는다.** 스내치 그룹에는 완료 경기 45건(2025년 18건,
2026년 27건)이 있는데 전부 시즌 미지정이다. "2026" 시즌을 만들어도 그 시즌에는 경기가 0건이다.

**2. 그래서 시즌을 지정하면 랭킹이 빈다.** 2026-08-18 운영에서 실제로 발생했다. 선택기의
기본값이 현재 시즌인데 그 시즌에 경기가 0건이라, 스내치의 랭킹·선수 페이지가 모든 방문자에게
빈 화면이 됐다. 현재 시즌을 해제해 원복했다. **시즌을 만든 직후에는 항상 이 구간이 생긴다.**

경기를 나중에 시즌에 넣을 수단이 필요하다.

## 무엇을 만드나

`/games`의 완료 경기 목록에서 **그룹장이 경기를 골라 시즌에 배정**한다. 여러 건을 한 번에
옮길 수 있고, 시즌 미지정으로 되돌릴 수도 있다.

## 설계 결정 요약

| 항목 | 결정 |
|---|---|
| 조작 위치 | `/games` 완료 경기 목록의 선택 모드 |
| 이동 단위 | 화면에서 **체크한 경기의 id 목록**. 날짜 범위는 조회 필터일 뿐 이동 기준이 아니다 |
| 대량 선택 | 날짜 범위 필터(페이징 없이 전부 로드) + "전체 선택(N건)" |
| 되돌리기 | `seasonId: null` 배정으로 시즌 미지정 복원 |
| 대상 | **완료(FINISHED) 경기만** |
| 스키마 | **변경 없음** |

### 왜 날짜 범위를 서버 이동 기준으로 쓰지 않나

`PUT`에 `{ from, to, seasonId }`만 보내면 요청이 가볍고 경기가 수천 건이어도 견딘다. 하지만
사용자가 화면에서 체크를 푼 경기까지 서버가 옮긴다 — **보이는 것과 실제 동작이 어긋난다.**
현재 최대 그룹이 45경기라 가벼운 요청의 이점이 없고, "고른 것만 움직인다"가 깨지는 대가가 크다.
날짜 범위는 **조회 필터로만** 쓰고, 이동은 명시적 id 목록으로 한다.

## 1. 백엔드

### 1.1 `PUT /game/season` (신규)

그룹장 전용 (`AuthGuard('jwt')`).

```ts
// 요청
{ groupId: number, gameIds: number[], seasonId: number | null }
// 응답
{ updated: number }
```

`seasonId: null`은 **시즌 미지정으로 되돌리기**다. 이것 때문에 배정 전체가 되돌릴 수 있는
조작이 되고, 그래서 확인 다이얼로그를 무겁게 걸지 않아도 된다.

**검증 세 가지 — 하나라도 어긋나면 전부 거부하고 아무것도 바꾸지 않는다:**

1. `assertSameGroup(req.user.groupId, dto.groupId)` — JWT의 그룹과 일치
2. `assertIdsInGroup(gameRepository, gameIds, groupId, ...)` — 모든 경기가 그 그룹 소유
3. `seasonId`가 `null`이 아니면 그 시즌이 그 그룹 소유

**부분 성공을 만들지 않는다.** "27건 중 26건만 옮겨졌습니다"가 제일 나쁜 상태다.

한 번의 UPDATE로 처리한다:

```sql
UPDATE game SET "seasonId" = :seasonId
WHERE id IN (:...gameIds) AND "groupId" = :groupId AND status <> 'DELETED'
```

`WHERE`에 `groupId`를 다시 거는 것은 방어적 중복이다(2번 검증이 이미 통과했다).

### 1.2 DTO

```ts
export class PutGameSeasonRequestDto {
  @IsNotEmpty() @IsNumber()
  groupId: number;

  @IsArray() @ArrayNotEmpty() @ArrayMaxSize(500)
  @IsInt({ each: true })
  gameIds: number[];

  // null은 시즌 미지정으로 되돌리기를 뜻하므로 null일 때 숫자 검증을 건너뛴다
  @ValidateIf((_, value) => value !== null)
  @IsInt()
  seasonId: number | null;
}
```

`ArrayMaxSize(500)`은 현재 규모(최대 45경기)에서 실질 제약이 아니지만, 상한 없는 배열을 받는
엔드포인트를 열어두지 않는다.

전역 `ValidationPipe`가 `whitelist` + `forbidNonWhitelisted`이므로 **DTO에 선언되지 않은
프로퍼티는 400**이다. `seasonId: null`이 정상 입력값이라는 점을 테스트로 고정한다
(시즌제 1단계에서 같은 실수를 한 번 했다).

### 1.3 `GET /game`에 날짜 범위 추가

기존 쿼리(`groupId`, `page`, `limit`, `status`) 옆에 `from`/`to`(`YYYY-MM-DD`)를 붙인다.

이 엔드포인트는 **DTO 클래스가 아니라 원시 `@Query('name')` 파라미터**를 쓴다
(`@Query('page') page?: string` 형태). 따라서 전역 ValidationPipe가 관여하지 않고,
`forbidNonWhitelisted` 함정도 해당되지 않는다. 같은 방식으로 `from`/`to`를 추가한다.

- 둘 다 없으면 기존 동작 그대로(무한 스크롤 페이징)
- 있으면 `game.date`가 그 범위에 드는 경기만 반환한다(양끝 포함)
- 선택 모드는 `page`/`limit` 없이 호출해 **범위 내 전부**를 받는다
- **형식·순서 검증은 컨트롤러에서 한다.** `YYYY-MM-DD`가 아니거나 `from > to`이면
  `BadRequestException`. DTO가 없으므로 자동 검증이 걸리지 않는다 — 검증을 빠뜨리면 잘못된
  문자열이 그대로 SQL 파라미터로 내려가 Postgres 에러(500)가 난다. 시즌제 1단계에서
  `seasonId=abc`가 정확히 이 경로로 500을 냈다.

### 1.4 `GET /game` 응답에 `seasonId` 포함

현재 `GameService.getGames`의 응답 객체에 `seasonId`가 없다. 목록에서 어느 경기가 어느 시즌인지
보여줄 수 없으므로 추가한다. 기존 소비자는 필드가 늘어나도 깨지지 않는다.

## 2. 프론트엔드

### 2.1 진입

`/games`의 완료 경기 섹션 헤더에 **"시즌 배정"** 버튼. `canManage`(그룹장)일 때만,
그리고 **그 그룹에 시즌이 1개 이상 있을 때만** 보인다 — 시즌이 없으면 드롭다운에
"시즌 미지정"밖에 없어 할 수 있는 게 없다. `SeasonSelector`가 시즌 0개일 때 숨기는 것과 같은
원칙이다.

### 2.2 선택 모드

**날짜 범위 필터** (상단)
- 시작일·종료일. 적용하면 페이징 없이 범위 내 완료 경기를 전부 불러온다.
- 비워두면 기존 무한 스크롤 목록 그대로.

**전체 선택**
- 체크박스 하나로 토글. 라벨에 **개수를 함께 적는다** — `전체 선택 (27건)`.
- 이 숫자는 **현재 로드된 경기 수**다. 날짜 범위를 적용했으면 범위 전체이고, 필터 없이
  스크롤 중이면 그때까지 로드된 수다.
- 필터가 없고 아직 더 불러올 게 남아 있으면(`hasMore`) 아래에 안내를 붙인다:
  **"아래로 더 있습니다 — 날짜 범위를 지정하면 한 번에 고를 수 있습니다"**

  이 한 줄이 "45건 중 20건만 로드된 상태에서 전체 선택을 누르고 45건을 골랐다고 믿는" 오해를
  막는다. 개수 라벨과 이 안내가 이 화면에서 가장 중요한 두 가지다.

**경기 카드**
- 선택 모드에서 왼쪽에 체크박스. 카드를 눌러도 선택된다(선택 모드에서는 기록 화면 이동을 막는다).
- **평소에도** 시즌이 배정된 경기에는 시즌명 배지를 단다. 배정 상태를 보려면 필요하고 배정
  결과를 바로 확인할 수 있다.

**하단 액션 바** — `frontend/src/app/teams/components/SelectionActionBar.tsx` 패턴을 따른다.
- `N건 선택됨` + 시즌 드롭다운(**시즌 목록 + "시즌 미지정"**) + `배정` + `취소`
- 선택 0건이면 `배정` 비활성화
- 확인 다이얼로그(`useConfirm`): "완료 경기 27건을 '2026' 시즌으로 옮깁니다."
  되돌릴 수 있는 조작이라 무겁게 막지 않는다.
- 성공 토스트: `27건을 '2026' 시즌에 배정했습니다.` → 선택 모드 종료 + 목록 갱신

### 2.3 진행 중 경기는 대상에서 뺀다

아직 끝나지 않은 경기라 시즌을 옮길 실익이 없고, 생성 시 현재 시즌이 자동으로 붙는다.
대상을 완료 경기로 한정하면 화면도 단순해진다.

## 3. 엣지 케이스

| 상황 | 동작 |
|---|---|
| `gameIds` 빈 배열 | 400. 프론트는 선택 0건이면 버튼 비활성화 |
| 삭제된 경기(`DELETED`) | 목록에 없고 UPDATE의 `WHERE`에서도 제외 |
| 존재하지 않거나 타 그룹의 `seasonId` | 403 |
| `gameIds`에 타 그룹 경기가 섞임 | 403, 아무것도 바뀌지 않음 |
| `from > to` | 400 |
| 두 관리자가 동시에 배정 | 단일 UPDATE라 나중 것이 이김. 되돌릴 수 있으므로 잠금 없음 |
| 시즌이 0개인 그룹 | "시즌 배정" 버튼 자체를 숨김 |

## 4. 테스트

백엔드는 실제 DB 없이 jest 목으로 작성한다(이 저장소의 기존 `*.spec.ts` 패턴).

- `game.service.season-assign.spec.ts`
  - 타 그룹 경기가 섞이면 거부하고 UPDATE를 호출하지 않는다
  - 타 그룹 시즌을 지정하면 거부한다
  - `seasonId: null`이면 시즌 검증을 건너뛰고 미지정으로 되돌린다
  - `updated` 카운트를 반환한다
- `game.repository` — `from`/`to`가 있으면 조건이 붙고 없으면 안 붙는다
  (`rankings.repository.spec.ts`의 조건부 `andWhere` 검증 패턴)
- `game.controller` — `from`/`to`의 형식 오류와 역순(`from > to`)이 400이 되는지.
  DTO 자동 검증이 없는 경로라 이 테스트가 유일한 안전망이다
- DTO 검증 — `seasonId: null` 통과, `seasonId: 'abc'` 실패
  (`season.request.dto.spec.ts` 패턴)

프론트엔드에는 테스트 러너가 없다. 검증은 `pnpm build`(타입체크 포함) + 수동 확인이다.
**이번에는 수동 확인을 건너뛰지 않는다** — 시즌제 1단계에서 건너뛴 결과가 위 배경의 2번이었다.

수동 확인 항목: 선택 모드 진입/취소, 날짜 범위 적용, 전체 선택 개수, `hasMore` 안내 노출,
배정 후 배지 갱신, 시즌 미지정으로 되돌리기, 시즌 0개 그룹에서 버튼이 안 보이는 것.

## 5. 배포

- **스키마 변경이 없다.** `synchronize: true` 리스크가 없다.
- 신규 엔드포인트라 **프론트가 먼저 나가면 404**다. 백엔드·프론트를 한 브랜치 한 머지로
  내보낸다(시즌제 1단계와 동일 — `deploy.yml`의 deploy 잡이 한쪽이라도 실패하면 스킵된다).
- 배포 후 `/games`를 직접 열어 스모크한다. CI 헬스체크는 `/group/all`과 프론트 루트만 본다.

## 6. 운영 순서 — 시즌을 실제로 시작할 때

이 기능이 있으면 배경의 2번(시즌 지정 시 랭킹이 빔)이 실질적으로 해소된다. 권장 순서:

1. 시즌을 만든다 (**현재 시즌으로 지정하지 않는다**)
2. `/games`에서 그 시즌에 속할 과거 경기를 배정한다
3. 랭킹에서 그 시즌을 골라 숫자가 맞는지 확인한다
4. 그때 현재 시즌으로 지정한다 — 화면이 채워진 상태로 시작한다

스내치의 경우 2025년 18건과 2026년 27건이 있으므로, "2025"·"2026" 두 시즌을 만들고 날짜
범위로 각각 배정하면 연도별 비교가 가능해진다.

## 7. 범위 밖

- 진행 중 경기의 시즌 변경
- 경기 생성 화면에서 시즌 직접 선택 (생성 시 현재 시즌 자동 귀속으로 충분)
- 시즌에 시작·종료일을 두어 자동 귀속시키는 방식 — 시즌제 1단계에서 뺀 결정을 유지한다
- 시즌제 2단계(경기↔팀 연결 + 팀 순위표), 3단계(팀 능력치)
